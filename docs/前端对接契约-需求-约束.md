# 前端对接契约、需求与约束

## 1. 文档目标

本文档面向 dashboard / Web 前端开发，明确当前阶段：

- 后端提供哪些事实数据
- 前端要生成哪些 view snapshot
- 首页、详情页、微观调控页分别吃什么数据
- 前端不负责什么
- 当前版本有哪些边界与约束

当前重点不是完整智能治理系统，而是：

> **先把 storage dashboard v1 做成开箱即用、可读、可纠偏，同时保留微观 drill-down 能力的宏观视图。**

---

## 2. 当前前端产品范围

当前前端需要承接两条路线：

### 2.1 Profile 编辑路线
负责：
- 编辑 `RoutingProfile`
- 消费 Query Builder metadata
- 生成合法 profile JSON

### 2.2 Storage Dashboard 路线
负责：
- 展示 AE2 网络的 storage snapshot
- 呈现 overview / storages / items / health
- 对“疑似无限 / 极端特殊节点”做最小人工纠偏
- 提供从宏观总览到单 storage / 单 item / 单 occurrence 的微观 drill-down 与调控入口

当前阶段，**Storage Dashboard 路线优先级更高**。

---

## 3. Dashboard v1 的产品目标

Dashboard v1 的目标不是完整治理，而是先做到：

1. 用户打开就能看到可用结果
2. 明显异常值不会严重污染首页判断
3. 用户能快速看出：
   - 网络有多大
   - 主存储在哪里
   - 哪些 item 存量最大
   - 哪些 item 有重复分布
   - 是否存在疑似无限 / 极端特殊节点
4. 若系统默认判断不对，用户可以低成本纠偏
5. 若用户需要继续下钻，可以进入单 storage / 单 item / 单 occurrence 的最小粒度观察与调控

一句话：

> **先给结果，再让用户修正；先给宏观，再允许微观下钻。**

---

## 4. 当前数据契约范围

当前前端主要消费两类后端事实数据，外加一类可选的 merge 结果展示数据：

### 4.1 `storageDump`
定位：
- 宏观事实层

用途：
- 首页 overview
- summary cards
- 首页四图
- largest storages
- item distribution summary
- health
- suspected semantic candidates

特点：
- 体量较小
- 已经带一定分析结果
- 适合作为首页与宏观页面主输入

### 4.2 `me dump`
定位：
- 微观事实层
- **v2 新增容量字段**：每个 cell 携带 `totalBytes` / `usedBytes` / `totalItemTypes` / `remainingItemTypes` / `cellKind` / `zoneId`

用途：
- 单 storage detail
- 单 item detail
- occurrence drill-down
- 最小粒度微观调控
- **存储健康诊断**：前端自行聚合计算 Zone/Bus/Cell 的容量使用率、类型耗尽风险、近满告警

特点：
- 体量更大
- 更接近原始事实
- 适合作为详情页和下钻页次级输入

### 4.3 `merge report`
定位：
- merge 结果展示层

用途：
- before / after 对比卡
- merge 效果复盘
- top benefit items
- 单物品 moved_out / merged_into 明细

特点：
- 当前是日志型产物
- 适合作为“快速 merge”结果展示输入
- 不属于 profile 编辑契约，也不是首页 storage dashboard 主输入

### 4.4 关于 raw dump 的边界
限制对象主要是：
- AI 协作
- 文档讨论
- 首页主流程

不是整个前端产品。

也就是说：
- **AI 协作、文档讨论、首页 overview 不要直接吞 1MB 级 raw `me dump`**
- **但 dashboard 的详情页、下钻页、微观调控页可以按需使用 `me dump` 或等价细粒度数据**

## 5. 前端生成 snapshot 的要求

这里的 “snapshot” 指：

> **前端基于 `storageDump` + `me dump` 生成的页面视图快照 / chart-ready view model。**

它不是新的事实源，也不是后端持久化契约，而是前端运行时派生层。

### 5.1 总体原则
- 后端负责生成**事实层数据**
- 前端负责生成**展示层 snapshot**
- 前端 snapshot 必须可重建、可追溯、不可冒充后端事实

### 5.2 前端 snapshot 的目标
前端生成 snapshot 的目的，是把后端事实数据整理成适合页面直接消费的结构，例如：

- 首页四图所需 series
- top N items 列表
- treemap nodes
- quantity buckets
- Lorenz curve series
- storage detail view model
- item detail view model
- occurrence table rows

### 5.3 前端 snapshot 的来源规则
前端生成 snapshot 时应遵守：

- 宏观 overview 优先使用 `storageDump`
- 细粒度 detail / drill-down 再按需读取 `me dump`
- 若 `storageDump` 已提供某字段，不要再从 `me dump` 重算一个口径不同的版本
- 前端派生结果必须能追溯到后端原始事实字段

### 5.4 前端 snapshot 必须是“可重建”的
要求：
- 可以根据当前 `storageDump` / `me dump` 重新生成
- 不依赖人工手改中间 JSON
- 不把前端聚合结果写回并冒充后端事实
- 不把图表聚合结果反向作为系统判定依据

### 5.5 前端 snapshot 的三层结构
推荐前端至少生成三类 view snapshot：

#### A. Overview Snapshot
用于：
- summary cards
- 首页四图
- 高亮 warnings

主要来源：
- `storageDump`

#### B. Storage Detail Snapshot
用于：
- 单 storage 页面
- top keys
- entry list
- storage review context
- 关联 suspected semantic candidate

主要来源：
- `storageDump` + `me dump`

#### C. Item Detail Snapshot
用于：
- 单 item 页面
- occurrences
- internal/external 分布
- 相关 storage links
- 细粒度微观调控上下文

主要来源：
- `me dump` + `storageDump`

`me dump` 不需要为了首页做额外裁剪，但它至少要让前端能够按需生成：

- 单 item occurrences
- 单 storage entries
- 单 storage total content review
- item -> storage 反查
- storage -> items 反查

前端从 `me dump` 至少需要稳定读取这些概念：
- `cells[]`
- `items[]`
- `items[].occurrences[]`
- `cells[].entries[]`
- item 的 `totalAmount`
- item 的 `occurrenceCount`
- storage/cell 的 `totalAmount`
- storage/cell 的 `distinctItemKeyCount`

如果后端后续愿意优化，也可以把 `me dump` 拆成更利于前端按需读取的细粒度接口，但当前不是强制要求。

前端不能自行推断或伪造：
- `locationId`
- `networkAmountShare`
- `fragmentationScore`
- `fragmentationLevel`
- `mixedInternalExternalItems`
- `suspectedSemanticCandidates`
- 任何系统判定类字段

这些必须由后端产出。

## 8. Dashboard v1 首页图表规范

首页固定展示四种图，不再让前端自由发散为任意图表组合。

### 8.1 Top Items by Amount
图表类型：
- **对数坐标水平条形图**

用途：
- 展示库存头部 item
- 解决 `2147483647 -> 64` 这种数量级差距

要求：
- 默认展示 top 15 或 top 20
- 必须明确标注 `log scale / 对数坐标`
- 数据源来自 `Overview Snapshot`
- 排序字段为 `totalAmount desc`

### 8.2 Item Composition
图表类型：
- **Treemap**

用途：
- 直观看网络存量主要被哪些 item 占据

要求：
- 对 `totalAmount <= maxStackSize` 的 item，不单独渲染
- 这些 item 合并为一个分组：`零散小量物品 / Small Items`
- 该分组至少显示：
  - 合并的 item 种类数
  - 合并后的总量
  - 占总量比例（若方便）
- 明细列表仍保留完整 item，不因图表聚合而丢失

### 8.3 Quantity Buckets
图表类型：
- **数量级分桶直方图**

用途：
- 展示 item 在不同数量级上的分布
- 体现长尾结构

建议分桶：
- `=1`
- `2 ~ maxStackSize`
- `maxStackSize+1 ~ 10^3`
- `10^3 ~ 10^4`
- `10^4 ~ 10^5`
- `10^5 ~ 10^6`
- `10^6+`

说明：
- 这里的 `maxStackSize` 按 item 自身栈上限理解，不固定写死为 64
- 该图的数据应由前端从事实数据生成 bucketed snapshot

### 8.4 Concentration
图表类型：
- **Lorenz Curve**

用途：
- 展示少数 item 是否主导了绝大多数库存
- 强化“宏观调控”而不是“仓库明细”的产品气质

要求：
- 旁边必须配一句自然语言解释
- 例如：
  - `前 10% 的物品种类占据了 87% 的总存量`
  - `库存高度集中于少数大宗资源`

### 8.5 首页图表的总约束
- 这四种图都基于 `Overview Snapshot` 渲染
- 不允许为了首页图表直接读取整份 raw `me dump`
- 首页图表应先可读、再可细查，不追求一次性展示全部细节
- 但这不否定 detail/drill-down 页面使用更细粒度数据

## 9. 疑似无限 / 特殊节点的当前契约

当前阶段只做**最小智能能力**，不要过度扩展。

### 9.1 当前支持的能力
后端会输出：
- `suspectedSemanticCandidates`

候选项当前主要用于：
- 疑似无限容器
- 极端主导或特殊大容量节点提示

### 9.2 前端当前必须支持的交互
对于高置信度候选，前端需要支持：
- 显示系统判断理由
- 显示当前默认处理状态
- 允许用户原地执行最小纠偏操作：
  - 确认它是特殊节点 / 无限节点
  - 标记它不是无限节点
  - 暂不处理

### 9.3 当前产品原则
- 高度可疑节点可以默认按 special / infinite-like 处理
- 这样首屏统计不会被明显污染
- 但用户必须能轻松改成“非无限”

即：

> **默认假定可以生效，但不能变成不可撤销的黑盒事实。**

---

## 10. 前端回写契约要求

当前前端需要预留“最小回写”能力。

前端回写时，不应提交整份大配置，而应尽量提交最小 payload。

建议最小结构至少包含：
- `locationId`
- `decisionType`
- `decisionValue`
- `note`（可选）
- `decidedAt`（可选）

典型动作包括：
- 标记为 infinite-like
- 标记为 non-infinite
- 清除人工覆盖

当前阶段前端应按“单条快速决策”设计交互，而不是要求用户进入复杂配置页。

---

## 11. 前端必须遵守的约束

### 11.1 不直接参与运行时执行
前端不负责：
- AE2 grid 扫描
- live storage 读取
- route 执行
- move 执行
- zone -> cell 选择

### 11.2 不自行发明业务枚举
前端不要手写、硬编码或自行扩展：
- field
- operator
- combinator
- route action
- zone kind
- storage semantic decision codes

应优先使用后端导出的契约值。

### 11.3 不把 dashboard 首页建立在全量原始 dump 上
原因：
- 数据量大
- 对首页无必要
- 不利于性能和维护
- 容易让 AI、文档流程或首页实现误把 raw dump 当成主 UI contract

正确做法：
- 首页吃 `storageDump`
- 首页图表吃前端生成的 `Overview Snapshot`
- 详情页分页或按需展开
- drill-down 再看 `me dump`
- `me dump` 可以作为**详情页 / 微观调控页的数据源之一**，但不是首页主数据源

### 11.4 不要求用户先完成复杂配置才能看到结果
这是当前最重要的 UX 约束之一。

前端不应把 dashboard 设计成：
- 先配置节点语义
- 再显示结果

而应设计成：
- 先显示可用结果
- 再允许用户在结果页面原地修正

## 12. Dashboard v1 推荐页面结构

### 12.1 Overview
用途：
- 看网络总体规模
- 看 health flags
- 看高亮异常
- 展示首页固定四图
- 消费前端生成的 `Overview Snapshot`

### 12.2 Storages
用途：
- 看 largest storages
- 看 internal / external 存储分布
- 看 storage location top keys
- 看 suspected semantic candidates 关联到哪些节点
- 进入单 storage detail，查看更细粒度条目与调控入口
- 消费前端生成的 `Storage Detail Snapshot`

### 12.3 Items
用途：
- 看 top amount items
- 看 duplicated items
- 看 fragmentation 重点对象
- 进入单 item detail，查看 occurrence 分布与微观调控上下文
- 消费前端生成的 `Item Detail Snapshot`

### 12.4 Health / Review
用途：
- 汇总 warnings
- 列出 suspected semantic candidates
- 让用户做最小纠偏操作

### 12.5 Detail / Drill-down
用途：
- 查看单 storage 的完整条目
- 查看单 item 的 occurrences
- 支持最小粒度的微观观察与调控
- 允许这里使用 `me dump` 或等价细粒度数据
- 优先消费前端派生出来的 detail snapshot，而不是让页面组件直接散读原始 JSON

---

## 13. 当前阶段明确不做的事

当前前端先不承担：
- 完整节点角色体系编辑器
- 复杂拓扑建模界面
- 全量智能建议系统
- 多层审批流
- 先做完语义建模再看 dashboard
- 把前端派生 snapshot 反向当成新的后端事实源

这些都属于 dashboard v1 之后的能力。

---

## 14. 后续扩展方向

在 dashboard v1 跑通后，再考虑逐步加入：
- 更完整的 storage node semantics
- 主仓 / bulk 仓 / legacy 外部仓等角色
- 更丰富的智能建议
- 更细的 overview 解释与 drill-down

当前不要让这些未来能力阻塞 dashboard v1。

---

## 15. 一句话结论

当前前端对接的核心目标是：

> **基于后端提供的 `storageDump`（宏观事实）与 `me dump`（微观事实），由前端生成 Overview / Storage Detail / Item Detail 三类 view snapshot，完成一个开箱即用且支持微观 drill-down 的 AE2 宏观 dashboard；首页和 AI 协作禁止误用 1MB 级 raw dump 作为主输入。**
