# 重构指南 (Refactoring Guide)

> 本文档记录项目中常见的重构模式、安全重构步骤和注意事项。
> 供 AI 协作者和开发者参考。

---

## 1. 重构基本原则

### 1.1 小步收口

- 每次重构只解决一个明确的问题
- 不要在一次重构中混合多个目标
- 每次重构后确保编译通过、测试通过

### 1.2 先读文档，再改代码

1. 阅读相关类职责文档（`docs/类职责/`）
2. 阅读架构边界文档（`docs/架构/FACTS.md`）
3. 阅读相关设计草案（如 `docs/历史文档-仅供AI参考/RuntimeTopology-设计草案.md`）
4. 理解当前职责后再动手

### 1.3 重构后同步文档

- 更新对应类职责文档
- 更新 `docs/类职责/索引.md`（若新增/删除类）
- 更新 `docs/架构/FACTS.md`（若影响架构边界）
- 更新 `docs/类职责总览.md`（若影响审查结论）

## 2. 常见重构模式

### 2.1 提取 Service 类

**场景**：一个类中混合了多个职责（如命令处理 + 业务逻辑 + 日志）。

**步骤**：
1. 识别可分离的职责（如日志输出、结果格式化）
2. 创建新的 Service/Utility 类，转移对应方法
3. 原类通过依赖调用新类
4. 更新类职责文档

**示例**：从 `SorterPlanService` 中提取日志逻辑到 `SorterPlanFileLogger`。

**检查清单**：
- [ ] 新类命名符合项目语义
- [ ] 新类放在正确的包路径下
- [ ] 新类的职责文档已创建
- [ ] `docs/类职责/索引.md` 已更新

### 2.2 统一日志基础设施

**场景**：多个 Logger 类有重复的格式化/写入逻辑。

**步骤**：
1. 识别公共模式（文件路径生成、时间戳格式化、JSON 序列化）
2. 提取到 `ReportFileSupport` 等共享工具类
3. Logger 类只保留业务相关的日志组装逻辑
4. 确保 Logger 不反向定义核心模型

**参考**：`ReportFileSupport.java` 提供了 `networkSlug()`、`writeTextFile()`、`buildCommandHeader()` 等共享方法。

**检查清单**：
- [ ] 共享逻辑提取后，Logger 类变薄
- [ ] Logger 不因提取而引入新的业务依赖
- [ ] 核心模型不因日志需求增加字段

### 2.3 拆分混合类

**场景**：一个类同时承担了 `route`、`zone`、`cell`、`execute` 中的多个职责。

**步骤**：
1. 识别每个职责对应的包路径
2. 创建新类，转移对应职责
3. 原类通过组合/委托调用新类
4. 确保新类放在正确的包下

**检查清单**：
- [ ] 拆分后每个类只属于一个包
- [ ] 没有跨层依赖违规
- [ ] 拆分后的类职责文档已创建

### 2.4 消除层穿透

**场景**：`rule/**` 包中的类引用了 `net.minecraft.*` 或 `appeng.*`。

**步骤**：
1. 识别被引用的 Minecraft/AE2 类型
2. 在 `ae2/` 层创建接口或适配器
3. `rule/` 层只依赖接口
4. `ae2/` 层实现接口并注入

**检查清单**：
- [ ] `rule/**` 不再导入 `net.minecraft.*` 或 `appeng.*`
- [ ] 接口定义在 `rule/` 或独立包中
- [ ] 实现类在 `ae2/` 中

### 2.5 统一命令处理模式

**场景**：多个命令的处理逻辑分散在 `SorterCommands.java` 中，内联逻辑过多。

**步骤**：
1. 每个命令对应一个 `application/` 下的 Service 类
2. Service 类接收 `CommandSourceStack` 和必要的 resolver
3. Service 返回统一的 `SorterFeedbackResult` 或专用 Result 类型
4. `SorterCommands.java` 只负责注册和参数解析

**参考**：`SorterPlanService`、`SorterMergeService`、`SorterDumpService`、`SorterStorageAnalysisService` 的模式。

**检查清单**：
- [ ] 每个命令有独立的 Service 类
- [ ] Service 类在 `application/` 包下
- [ ] 返回类型统一（`SorterFeedbackResult` 或专用 record）

### 2.6 统一网络包模式

**场景**：多个网络包的处理逻辑分散，序列化/反序列化模式不统一。

**步骤**：
1. 每个网络包是一个 `record` 实现 `CustomPacketPayload`
2. 使用 `StreamCodec` 定义序列化/反序列化
3. handler 类只负责分发，不包含业务逻辑
4. 在 Mod 主类中注册所有网络包

**参考**：`SorterCommandPayload`、`SorterAnalysisPayload`、`FileChunkPayload` 的模式。

**检查清单**：
- [ ] 网络包是 `record` 类型
- [ ] 使用 `StreamCodec` 而非手动读写
- [ ] handler 不包含业务逻辑
- [ ] 网络包已注册到 `AppliedStorageSorter.java`

## 3. 安全重构步骤

### 3.1 重构前

1. **阅读文档**：理解当前类的职责和边界
2. **阅读源码**：理解当前实现
3. **确认范围**：明确要改什么、不改什么
4. **备份**：确保有 git 提交或 stash

### 3.2 重构中

1. **小步提交**：每完成一个原子改动就编译验证
2. **保持接口**：尽量不修改公开 API 签名
3. **逐步迁移**：先新增，再迁移调用方，最后删除旧代码
4. **持续验证**：每次改动后 `./gradlew compileJava`

### 3.3 重构后

1. **编译验证**：`./gradlew compileJava`
2. **测试验证**：`./gradlew test`
3. **文档同步**：更新所有受影响的文档
4. **清理**：删除废弃代码和注释

## 4. 不建议的重构

| 重构类型 | 原因 | 替代方案 |
|---------|------|---------|
| 为单一实现提取接口 | 增加不必要的抽象层 | 等到有第二个实现再提取 |
| 重写稳定代码以匹配"未来架构" | 浪费精力，可能永远用不上 | 只改当前需要改的 |
| 大范围重命名 | 破坏 git 历史追踪 | 小范围、分批次重命名 |
| 合并多个 Logger | 职责分离是设计意图 | 提取公共工具类即可 |
| 提前拆分 Analyzer | 当前分析系统还很薄 | 等分析逻辑膨胀后再拆 |

---

## 5. 重构优先级

| 优先级 | 类型 | 说明 |
|--------|------|------|
| P0 | 层穿透修复 | rule 层引用 Minecraft/AE2 类，必须立即修复 |
| P1 | 职责混淆 | 一个类混合 route/zone/cell/execute，尽快拆分 |
| P2 | 代码重复 | 多个类有重复逻辑，提取共享工具 |
| P3 | 命名不一致 | 命名与项目语义冲突，逐步修正 |
| P4 | 过度抽象 | 接口/抽象类只有单一实现，暂不处理 |

---

> **一句话原则**：小步收口，少做幻想式重构；每次重构只解决一个明确的问题。
