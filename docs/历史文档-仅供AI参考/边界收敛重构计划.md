# 边界收敛重构计划

## 1. 目标

本次重构的目标不是扩张抽象，也不是重写功能，而是进行一次**边界确定型收敛重构**。

目标只有四个：

1. 让 `application` 成为唯一清晰的用例编排层
2. 让 `rule` 回到纯规则语义层
3. 让 `ae2` 回到 AE2 集成 / 运行时 / 执行能力层
4. 降低作者与 AI 协作者恢复上下文时的认知负担

一句话：

> 把当前“能工作但有点膨胀”的结构，收敛成“边界硬、定位快、可继续维护”的结构。

---

## 2. 本次重构明确不做的事

以下事项**不属于本次重构范围**：

1. 不重写 `/sorter merge` 为 zone 主线的一部分
2. 不引入新的大一统抽象框架
3. 不重写 `DriveMachineAccessor`
4. 不优先做命名美化或风格统一
5. 不先动 GUI / menu / blockentity 主体结构
6. 不改变现有命令语义：
   - `/sorter merge`
   - `/sorter me dump`
   - `/sorter me storageDump`
   - `/sorter me bindProfile`
   - `/sorter me showProfile`
   - `/sorter me plan`
   - `/sorter me planAndMove`

---

## 3. 当前问题总结

### 3.1 已确认的核心稳定边界

以下部分当前判断为**架构稳定核心**，原则上不做语义重写，只做最小收口：

- `rule/filter/**` 的核心过滤模型与匹配逻辑
- `rule/route/RoutingEngine`
- `rule/route/RoutingProfile` 及规则模型
- `plan/**` 规划结果模型
- `ae2/zone/RuntimeZone`
- `ae2/zone/RuntimeCell`
- `ae2/zone/RuntimeTopology`
- `ae2/sort/**` 快速 merge 路径
- `blockentity/DigitalAssetVaultBlockEntity`
- `item/DigitalAssetManagementCardItem`

### 3.2 已确认的主要问题

1. `application` 层是存在的，但还不是唯一编排中心
2. `rule/**` 包中混入了 repository / json codec / cli 等基础设施内容
3. `application/**` 中混入了 persistence store 类型
4. `LiveZoneAllocationPlanner` 同时承担 live 扫描、聚合、route 输入构造、plan 生成
5. `Ae2ZoneMoveExecutor` 单类承担过多职责
6. `SorterPlanFileLogger` 与 `SorterFileLogger` 文本构建逻辑偏胖
7. 命令结果模型不统一，导致 command 层反馈处理方式分裂
8. `ae2/scan/**` 中混入了对 DAV zone 声明语义的直接感知

---

## 4. 重构硬规则

重构期间必须始终满足以下规则：

1. `rule/**` 不得依赖 Minecraft / AE2 运行时类型
2. `application/**` 不得直接持有持久化实现细节
3. `application/**` 负责用例编排，不负责底层 cell 操作细节
4. `ae2/**` 不得定义 route 规则语义
5. `analysis/**` 不得发起执行行为
6. `/sorter merge` 仍然保持为独立产品路径
7. 任何新拆出的类，必须能清楚回答“属于哪一层”

## 7. 执行阶段

## 阶段 0：冻结边界与安全护栏

### 目标

在真正改代码前，先冻结本次重构的边界规则与非目标。

### 操作

1. 以本文件为准，确认重构范围
2. 不在本阶段做行为改动
3. 如有必要，补充 docs 中的架构边界说明

### 完成标准

- 重构期间不再临时扩张目标范围

---

## 阶段 1：统一 application 输出模型

### 目标

让 command 层面对一致的应用结果模型，减少分裂的反馈处理逻辑。

### 当前问题

当前结果类型包括：

- `SorterFeedbackResult`
- `SorterDumpCommandResult`
- `SorterMergeCommandResult`
- `SorterStorageAnalysisCommandResult`

它们的字段风格和反馈形态不统一。

### 重构动作

1. 设计统一的 application result 风格
2. 保证所有 command-facing use-case 返回一致结构
3. 让 command 层反馈逻辑统一
4. 避免在 application service 中过早格式化过多命令文本

### 约束

- 不改变命令语义
- 不改变外部用户看到的核心反馈信息
- 可以调整返回模型内部结构

### 完成标准

- `SorterCommands` 中不再为不同命令维护明显分裂的结果处理模式
- application 结果模型收敛为一套主风格

---

## 阶段 2：把基础设施从 `rule/**` 与 `application/**` 中迁出

### 目标

恢复 `rule/**` 的纯度，恢复 `application/**` 的 use-case 语义。

### 重构动作

1. 迁出 `RoutingProfileRepository`
2. 迁出 `RoutingProfileJsonCodec`
3. 迁出 `RoutingProfileJsonCli`
4. 迁出 `FilterUiMetadataJsonCodec`
5. 迁出 `FilterUiMetadataCli`
6. 迁出 `NetworkProfileBindingStore`
7. 修正全部引用
8. 更新 docs 中的类职责文档（如已存在对应文档）

### 迁移原则

- 先迁包，后清理命名
- 尽量不改内部实现
- 以边界清晰优先于命名完美

### 完成标准

- `rule/**` 中不再出现 repository / cli / json codec / 文件系统职责
- `application/**` 中不再承担持久化 store 的物理实现放置职责

---

## 阶段 3：收 application 为真正的 use-case 层

### 目标

让 `application/**` 只保留“用例编排”职责。

### 重构动作

1. 审视以下类的职责边界：
   - `SorterPlanService`
   - `SorterProfileBindingService`
   - `SorterDumpService`
   - `SorterStorageAnalysisService`
   - `SorterMergeService`
2. 把可复用的前置校验抽出为轻量 helper 或 command precondition 工具
3. 明确每个 service 是否只负责单一 use-case
4. 避免 service 同时承担：
   - 持久化读写实现
   - 复杂文本拼装
   - 过多 infra 细节判断

### 原则

- 不追求 service 数量增加
- 不为了“看起来分层”而创造空壳类
- 仅在职责明显混杂时做切分

### 完成标准

- `application/**` 中的主要类可以被明确描述为用例
- 每个 use-case 的依赖方向更加清晰

---

## 阶段 4：拆解 `LiveZoneAllocationPlanner`

### 目标

把 live 网络事实提取与 route 规划分开。

### 当前问题

`LiveZoneAllocationPlanner` 当前同时做：

1. live storage 遍历
2. item 聚合
3. route context 构造
4. assignment 生成
5. `ZoneAllocationPlan` 构建

### 重构动作

1. 拆分“live item aggregation”与“routing plan generation”两个步骤
2. 保证 route 规划只依赖必要的 item 事实视图
3. 减少 AE2 live 扫描细节与 route 语义拼装混在一个类内

### 约束

- 不改变 `ZoneAllocationPlan` 语义
- 不改变 `RoutingEngine` 的输入语义
- 不新增无意义大抽象

### 完成标准

- `LiveZoneAllocationPlanner` 不再同时承担所有步骤
- 代码中能明确区分“扫描事实”和“生成规划”

---

## 阶段 5：拆解 `Ae2ZoneMoveExecutor`

### 目标

降低执行层的认知密度，使单点修改不再必须重新阅读整个执行器。

### 当前问题

`Ae2ZoneMoveExecutor` 当前同时做：

- assignment 索引
- source drives 遍历
- stack 扫描
- placement 请求
- extract / insert / rollback
- sample message 构建
- debug 统计
- detailed result 组装

### 重构动作

至少拆成以下几个职责单元：

1. assignment / fingerprint 索引
2. source cell / source stack 枚举
3. 单次 move attempt 执行
4. debug 统计与 sample 收集
5. result 组装

### 原则

- 不引入复杂框架
- 优先提取明确的小类或私有静态 helper
- 保持现有行为与日志语义尽量稳定

### 完成标准

- `Ae2ZoneMoveExecutor` 主体显著瘦身
- 单次移动逻辑与统计逻辑分开
- 后续修改 placement / fingerprint / rollback 时不必重读整个类

---

## 阶段 6：切断 `ae2/scan` 对 DAV zone 语义的直接感知

### 目标

让扫描层回到“发现事实”，让 zone 声明解释回到 runtime zone 构建侧。

### 当前问题

当前 `DriveMachineAccessor` 中的 `getDeclaredZoneId()` 直接知道 `DigitalAssetVaultBlockEntity`。

### 重构动作

1. 识别 `DriveMachineAccessor` 中哪些逻辑属于纯扫描事实
2. 把 zone declaration 解释迁移到 `RuntimeZoneRegistryBuilder` 或更合适的 zone/runtime 侧
3. 保持 `DriveMachineAccessor` 尽量只提供：
   - blockId
   - storage
   - slot
   - attachment
   - host
   - external/internal 事实

### 约束

- 不重写 `DriveMachineAccessor` 整体策略
- 不改变当前支持对象集合
- 仅减少语义泄漏

### 完成标准

- `ae2/scan/**` 不再直接承载 DAV zone 声明语义
- zone 解释逻辑回归 zone/runtime 侧

---

## 阶段 7：收 logger

### 目标

减轻 `SorterPlanFileLogger` 与 `SorterFileLogger` 的文本构建负担。

### 重构动作

1. 提取共享 header builder
2. 提取 target/grid 格式化 helper
3. 提取 drive/cell reference 格式化 helper
4. 提取共享写文件逻辑（如有必要）
5. 减少跨 logger 的重复文本拼接模式

### 原则

- 不创建新的大 logging 框架
- 不影响当前日志格式的核心可读性
- 优先减少重复与肥大方法

### 完成标准

- logger 仍然是 logger，不再像半个格式化子系统
- 共享逻辑被提取，重复显著下降

## 9. 验收标准

本次重构完成后，应满足以下标准：

### 9.1 边界标准

1. `rule/**` 中只保留纯规则语义相关类型
2. `application/**` 中主要类都可被明确描述为 use-case
3. `ae2/**` 中执行、扫描、runtime 的职责更清晰
4. `analysis/**` 仍保持观察者定位

### 9.2 认知标准

作者或 AI 协作者应能在短时间内回答：

1. 这个类属于哪一层？
2. 这条命令由谁编排？
3. 这个模型是规则语义还是运行时事实？
4. 这个类为什么存在？

### 9.3 行为标准

以下能力语义保持不变：

- `/sorter merge`：快速 merge 模式
- `/sorter me dump`：网络 dump
- `/sorter me storageDump`：storage analysis dump
- `/sorter me bindProfile`：网络绑定 profile
- `/sorter me plan`：生成 plan
- `/sorter me planAndMove`：生成 plan 并执行 move

### 9.4 维护性标准

应明显降低以下痛点：

- 修改执行逻辑时必须重读整个 `Ae2ZoneMoveExecutor`
- 修改 live plan 时必须同时理解扫描与 routing 全部细节
- 阅读 `rule/**` 时混入 repository / json / cli 心智噪声
- command 层因结果模型分裂而存在多套反馈处理方式

---

## 10. 最终原则

如果某个改动让架构图更漂亮，但让边界更模糊、类更多、恢复上下文更慢，则该改动不应被接受。

本次重构的唯一评价标准是：

> 是否让项目重新变得可压缩、可定位、可维护。
