# 下一步计划

## 1. 当前阶段判断

从功能闭环来看，这个项目已经不再处于“先把骨架立起来”的阶段，而是进入了：

> **可发行版本的整理与收口阶段。**

已经跑通的主线包括：

- DAV 作为 zone 声明入口
- 管理卡携带 `zoneId`
- 全局 profile 绑定到当前 ME 网络
- live plan 生成
- runtime zone registry 构建
- `planAndMove` 实际搬运
- 详细日志输出

所以接下来的重点，不再是继续发明大抽象，而是：

- 收口现有边界
- 文档化现有能力
- 处理少量遗留技术债
- 提升发行可用性

---

## 2. 近期优先级

### A. 文档与发布包装
优先补齐：

1. README / 使用说明
2. 示例 profile
3. zoneId 命名规范
4. DAV + 管理卡 + `bindProfile` + `planAndMove` 的最小操作流程
5. 类职责文档的持续维护入口
6. storage dashboard / 存储节点语义文档

这是最接近“可发行”的工作。

### B. 统一命名与反馈
优先处理：

- `vanilla` / `vanilla_zone` 这类命名不一致风险
- 命令返回文本是否足够让玩家理解当前状态
- 关键失败信息是否能直接指向原因

### D. storage dashboard / 节点语义主线
当前已开始形成一条新的长期主线：

- `/sorter me storageDump`
- storage analyzer snapshot
- web dashboard
- 存储节点语义确认
- world save override

近期判断：

- 先把 analyzer 输出稳定成 dashboard-first contract
- 先从“疑似无限容器”这类高价值语义节点做起
- analyze 只负责提出候选与理由，不替用户做最终判定

### 3.1 `DriveMachineAccessor`
现状：

- 用反射统一访问不同 drive-like machine
- 用 block id 白名单识别支持对象

判断：

- 这是当前阶段合理的工程折中
- 但它是明确技术债，版本升级时要重点回归

### 3.2 merge 链路
现状：

- `MergeMovePlanner` 仍在服务 `/sorter merge`
- 新路径已经是 zone 驱动的 plan/move 模型

判断：

- 现在不是立刻重写它
- 而是明确它的产品定位：**快速 merge 模式**

### 3.3 文档与测试样例
现状：

- 核心逻辑已经能跑
- 但发行层面的说明、示例和回归样例还不够完整

判断：

- 这是最值得投入的下一阶段工作

---

## 4. 当前明确不做的事

近期先不做：

- 再引入一层更大的运行时框架
- 先设计一套抽象 sorter 家族再说
- 为未来可能出现的存储节点做大一统拓扑系统
- 为“也许以后会用到”而重写现有清晰类

一句话：

> **现在要做的是收口，不是扩张。**

---

## 5. 当前的判断标准

新增结构前先问：

1. 它是不是在解决已经出现的真实问题？
2. 它会不会破坏现在已经很清楚的边界？
3. 它是让发布更稳，还是只是让架构图更好看？

只有这三条都过了，才值得继续加。

---

## 6. 一句话结论

下一步最值钱的工作不是继续堆系统，而是：

> **把已经跑通的主链路包装成一个别人真的能装、能配、能排错、能上手的发行版。**
