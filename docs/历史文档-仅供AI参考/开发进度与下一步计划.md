## 3. 已确认的设计决策

### 3.1 能力拆分：自动整理 vs 自动搬运

当前已经明确，这个 mod 后续将稳定分成两条能力线：

#### 自动整理
- 无需复杂用户配置
- 只负责把同一种物品从多个盘中归并到最小足够容纳它的盘
- 不替玩家猜测物品语义分类
- 不自动决定这个东西属于哪个“区域”

一句话：

- **自动整理 = 内部 drive / cell 级归并与压实**

#### 自动搬运
- 必须由玩家手动配置
- 玩家定义存储区
- 玩家定义过滤器
- 玩家定义应用顺序与默认去向
- 命中后定向送往对应存储区

一句话：

- **自动搬运 = 玩家显式指定去向的规则路由**

### 3.2 当前过滤系统核心抽象

当前已经明确过滤系统的核心不是“纯规则长表”，而是以下最小稳定骨架：

1. **存储区（StorageZone）**
   - 表示逻辑目标
   - 解决“物品应该去哪”

2. **过滤器（ItemFilter）**
   - 表示匹配条件集合
   - 内部已升级为树形表达式（group / rule）
   - 解决“什么物品会命中”

3. **路由规则（RouteRule）**
   - 把过滤器和存储区连接起来
   - 解决“命中后怎么处理、是否继续后续规则”

4. **配置剖面（RoutingProfile）**
   - 表示一整套可导入导出的 routing 配置

也就是说，执行配置层面当前已经正式收敛为：

- 存储区
- 过滤器
- 路由规则
- 默认去向
- profile JSON

### 3.3 标签过滤的定位

当前已明确：

- 会支持 **按标签过滤**
- 但不会引入独立的“标签中间层”系统
- tag 只是过滤器支持的一种匹配方式

这意味着当前更合理的过滤方式集合会是：

- item id
- mod id
- tag
- 名称匹配
- component 状态
- 其他后续扩展项

### 3.4 明确不做的 UI 方向

已经确认：

- **不做流程编辑器**
- **不做图形化编程式节点拼装**
- **不做低代码工作流工具**

当前更合适的 UI/UX 边界是：

- 列表 / 表单负责编辑
- 只读流程图负责解释顺序与去向

### 3.5 当前 UI/UX 原则

已经明确：

- 每个页面都要有清晰 tooltip
- 过滤相关控件要有详细 tooltip
- 要提供足够完整的 GuideME / 游戏内说明
- 主界面尽量少堆概念，悬浮解释负责讲细节，GuideME 负责系统教学

### 3.6 runtime network id 方案（继续暂缓）

之前曾计划优先做：

- `/sorter list`
- `/sorter once <runtimeId>`
- runtime network id 分配器

当前阶段继续暂缓，原因不变：

- `/sorter me` 与 `/sorter me dump` 仍是更小、更稳、更高价值的入口
- 在自动整理 / 自动搬运模型未稳定前，优先做 runtime id 收益不高

## 5. 当前产品方向判断

### 5.1 目标用户边界已经比较清晰

当前项目并不是面向所有 AE2 使用者。

明确不属于主要目标用户的包括：

- 把 AE2 当“大号终端/大号箱子”来用的轻度用户
- 不愿意装 AE2 附属模组的轻度仓储用户
- 以冒险/RPG 为主、没有复杂自动化需求的整合包玩家

当前更明确的目标用户是：

- 把 AE2 当基地主仓储系统的人
- 会做自动化输入输出的人
- 会装 AE2 扩容/增强附属的人
- 会长期维护大型网络、子网、物流拓扑的人
- 对系统可控性、结构整洁度、路由稳定性有要求的人

一句话概括：

- **目标用户不是 AE2 轻度使用者，而是深度 AE2 玩家 / AE2 系统经营者。**

### 5.2 当前主要价值不应再以“性能优化”作为主叙事

最近的讨论已经确认一个现实判断：

- 在现代整合包与现代硬件环境下，AE2 主网通常已经不是那么容易被性能问题逼到必须优化
- 即使在大型整合包中，单个主网往往也能正常运行
- 因此“减少 dirty / 减少主网写入 / 少一次重扫”这类收益，通常不足以成为主要装机理由

因此当前更合理的定位是：

- **性能优化是副收益，不是主卖点**

主价值应该是：

- 更可控
- 更少维护
- 更统一
- 更可解释
- 更符合深度 AE2 玩家对系统治理的需求

### 5.3 当前主要价值也不应再以“省盘容量”作为主叙事

已经确认：

- 现代资源环境下，多造盘往往不是问题
- Advanced Cells / Mega Cells 类模组会进一步降低“省容量”价值
- 因此单纯依赖“整理碎片、省几块盘”的理由，不足以支撑强卖点

因此更合理的价值表述应为：

- **不是帮玩家省几个盘，而是帮玩家降低大型 AE2 系统的维护混乱度。**

### 5.4 当前最有潜力的价值主轴

当前已经逐渐收敛出的高价值方向有：

1. **自动整理：内部盘归并 / 聚合**
2. **自动搬运：存储区 + 过滤器 + 应用顺序**
3. **dump + 离线分析驱动规则设计**
4. **面向深度 AE2 玩家的一致性存储治理**

## 6. 中长期产品畅想（基于最近讨论整理）

### 6.1 自动整理后续演进

自动整理未来的重点不会是“有没有整理”，而是：

- destination 怎么选更合理
- 怎么定义“最小足够容纳”
- 是否需要容量预占
- 是否需要更稳的移动排序
- 如何避免整理结果反复波动

### 6.2 自动搬运长期方向

当前已经明确一个长期方向：

- 玩家划分存储区
- 玩家定义过滤器
- 玩家设置应用顺序
- 玩家查看只读流程图解释结果
- 玩家通过 tooltip 与 GuideME 理解系统

这条路线比“图形化流程编辑器”更符合本项目气质，也更现实可维护。

### 6.3 dump、规则模型、生成器与分析器的长期价值

当前已经证明：

- 真实网络 dump 是规则设计的核心样本
- 纯 Java 规则模型可以独立于 Minecraft 环境演进
- 路由 profile JSON 可以作为未来 React/Web 配置端的共享交换格式
- 现在已经补上 routing profile / network dump 两份 JSON Schema，可作为前后端和脚本工具之间的稳定结构契约
- filter 已升级为树形表达式模型，可直接贴近 React Query Builder 的 group/rule 结构
- 还可以从 Java 侧导出 Query Builder field/operator/combinator metadata，避免前端自行发明常量
- fallback suggestion 已经可以反推出“优先补哪些规则”
- profile generation 已经被抽象为 analyzer 可调用的稳定接口，而不是写死在某个具体实现里

离线分析器当前可以帮助判断：
  - 哪些 item 适合 bulk
  - 哪些 mod / tag 占比高
  - 哪些物品带 components
  - 哪些规则值得优先支持
  - 哪些 fallback item / fallback mod 最值得补规则

因此 dump / analyzer / routing model 不只是调试工具，而是：

- **后续过滤设计与 UX 决策的数据基础设施**
- **未来配置生成器与智能 suggestion 的基础设施**
- **未来更智能 analyzer / generator 实现可复用的接口基础设施**

## 7. 当前推荐的近期计划


### 阶段 A：建立统一运行时模型

当前优先级最高。

目标：










- 引入以 cell 为中心的运行时模型：
  - `RuntimeCell`
  - `RuntimeZone`
- 让 DAV、原版 Drive、ExtendedAE drive 最终都被解析成统一的 cell 集合
- 明确：
  - **最终管理对象是 cell**
  - DAV 只是带可选治理语义的 cell 容器
- 让已插入 Zone Card 的 DAV 在运行时被归入对应 zone


### 阶段 B：重构 sorter 体系

目标：







- 把当前 `SorterMovePlanner` 提炼成：
  - `AbstractSorter`
  - `MESorter`
  - `ZoneSorter`
- `MESorter` 负责整个 ME 网络中**未声明 zone** 的 cells
- `ZoneSorter` 负责某个 `RuntimeZone` 内部的 cells
- DAV 在插入 Zone Card 后，其内部整理由 `ZoneSorter` 接管


### 阶段 C：收缩 executor 职责


目标：


- executor 不再承担 zone 内深度整理逻辑
- executor 只负责：
  - 接受 `item -> zone` 指令
  - 把物品送到目标 zone 的某个可接收 cell
- zone 内部压实与归并交给 `ZoneSorter`





### 阶段 D：继续稳定 dump / profile / planner 链路


当前已具备：




- dump-based `ZoneAllocationPlanner`
- 详细文本 analyzer
- 可先离线验证 `item -> zone` 分类结果


下一步重点：


- 让运行时稳定读取实例中的 profile 文件
- 让 planner / executor / sorter 共用统一的 runtime cell / zone 模型






### 阶段 E：再继续做 suggestion 与 UI


在运行时模型和 sorter 分层稳定后，再继续：


- suggestion 强化
- profile 生成器增强
- GUI / Web 配置端联动
