## 3. 修改建议

### 3.1 架构与设计层面

#### 3.1.1 [`DriveMachineAccessor`](../类职责/ae2/scan/DriveMachineAccessor.md) 反射层 — 建议引入 AE2 API 的 `IChestOrDrive` 接口替代反射

| 项目 | 内容 |
|------|------|
| **问题** | [`DriveMachineAccessor.java:77-79`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/scan/DriveMachineAccessor.java#L77) 使用反射调用 `getCellCount()`、`getOriginalCellInventory()`、`getCellInventory()` 方法。AE2 的 `IChestOrDrive` 接口（位于 `appeng.api.implementations.blockentities.IChestOrDrive`）已经提供了这些方法的编译时契约 |
| **建议** | 优先尝试通过 `IChestOrDrive` 接口访问，反射作为 fallback。这能减少运行时反射开销，提高上游兼容性 |
| **影响范围** | [`ae2/scan/DriveMachineAccessor.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/scan/DriveMachineAccessor.java) |
| **优先级** | 🔴 高 |

#### 3.1.2 [`RuntimeTopology`](../类职责/ae2/zone/RuntimeTopology.md) 的 `diagnostics` 字段 — 当前被硬编码为空列表

| 项目 | 内容 |
|------|------|
| **问题** | [`RuntimeZoneRegistryBuilder.buildTopology()`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/RuntimeZoneRegistryBuilder.java) 传入 `java.util.List.of()` 作为 diagnostics。这意味着 [`RuntimeTopology`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/RuntimeTopology.java) 的 diagnostics 永远为空，失去了"胖 topology"设计原则中 diagnostics 的应有价值 |
| **建议** | 在 `buildTopology()` 过程中收集实际的诊断信息（如：未分配 cell 的数量、重复 zoneId 冲突、DAV 声明异常等），填充 diagnostics 列表 |
| **影响范围** | [`ae2/zone/RuntimeZoneRegistryBuilder.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/RuntimeZoneRegistryBuilder.java)、[`ae2/zone/RuntimeTopology.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/RuntimeTopology.java) |
| **优先级** | 🟡 中 |

#### 3.1.3 [`MergeMovePlanner`](../类职责/ae2/sort/MergeMovePlanner.md) 的 `firstCellByKey` 策略 — 可能导致次优合并

| 项目 | 内容 |
|------|------|
| **问题** | [`MergeMovePlanner.plan()`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/sort/MergeMovePlanner.java) 使用 `firstCellByKey.putIfAbsent()` 记录第一个遇到的 cell 作为目标。如果第一个 cell 容量已满或类型数已满，后续的 SIMULATE insert 会返回 0，导致该物品的所有合并都被跳过 |
| **建议** | 当 SIMULATE 返回 0 时，尝试寻找下一个可容纳的 cell 作为目标，而不是直接跳过该物品的所有后续副本 |
| **影响范围** | [`ae2/sort/MergeMovePlanner.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/sort/MergeMovePlanner.java) |
| **优先级** | 🟡 中 |

#### 3.1.4 [`SorterMoveOperation`](../类职责/ae2/sort/SorterMoveOperation.md) 的 rollback 策略 — 部分插入回滚后未标记失败

| 项目 | 内容 |
|------|------|
| **问题** | [`SorterMoveOperation.execute()`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/sort/SorterMoveOperation.java) 在 `inserted < extracted` 时执行回滚，但回滚后 `failedMoveCount` 未递增（仅当 `inserted != plannedMove.amount()` 时递增）。如果 `inserted > 0` 但 `< plannedAmount`，回滚后 `completedMoveCount` 和 `failedMoveCount` 都可能不准确 |
| **建议** | 回滚后应明确标记为失败，并记录回滚是否成功。当前 `rollbackFailedCount` 在 [`Ae2ZoneMoveExecutor`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/Ae2ZoneMoveExecutor.java) 中声明但从未被赋值 |
| **影响范围** | [`ae2/sort/SorterMoveOperation.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/sort/SorterMoveOperation.java)、[`ae2/zone/Ae2ZoneMoveExecutor.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/Ae2ZoneMoveExecutor.java) |
| **优先级** | 🔴 高 |

### 3.2 代码质量与可维护性

#### 3.2.1 [`Ae2StorageAnalyzer`](../类职责/ae2/analysis/Ae2StorageAnalyzer.md) 的 `ItemAccumulator` — 内部类可提取为独立类型

| 项目 | 内容 |
|------|------|
| **问题** | [`Ae2StorageAnalyzer`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/analysis/Ae2StorageAnalyzer.java) 长达 447 行，内部包含 `ItemAccumulator` 私有类（403-445 行）。该类逻辑相对独立（累加器模式），提取为包级可见的独立类可提高可测试性 |
| **建议** | 将 `ItemAccumulator` 提取为 `ae2/analysis/ItemAccumulator.java`，并为其编写单元测试 |
| **影响范围** | [`ae2/analysis/Ae2StorageAnalyzer.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/analysis/Ae2StorageAnalyzer.java) |
| **优先级** | 🟢 低 |

#### 3.2.2 [`LiveZoneAllocationPlanner`](../类职责/ae2/zone/LiveZoneAllocationPlanner.md) 的 `LiveItemBuilder` — 与 `Ae2StorageAnalyzer.ItemAccumulator` 存在重复模式

| 项目 | 内容 |
|------|------|
| **问题** | [`LiveZoneAllocationPlanner`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/LiveZoneAllocationPlanner.java) 的 `LiveItemBuilder` 和 [`Ae2StorageAnalyzer`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/analysis/Ae2StorageAnalyzer.java) 的 `ItemAccumulator` 都实现了"遍历存储 → 聚合物品 → 生成摘要"的模式，但各自独立实现 |
| **建议** | 考虑提取一个共享的 `ItemAggregator` 工具类，减少重复代码。但需注意不要过度抽象（遵循项目"不要强行抽象"原则） |
| **影响范围** | [`ae2/zone/LiveZoneAllocationPlanner.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/LiveZoneAllocationPlanner.java)、[`ae2/analysis/Ae2StorageAnalyzer.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/analysis/Ae2StorageAnalyzer.java) |
| **优先级** | 🟢 低 |

#### 3.2.3 [`ZoneMergePlanner`](../类职责/ae2/zone/ZoneMergePlanner.md) 的 `ItemFingerprint` — NBT 序列化性能开销 ✅ 已实现

| 项目 | 内容 |
|------|------|
| **问题** | [`ZoneMergePlanner.fingerprintOf()`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/ZoneMergePlanner.java) 对每个 item 调用 `stack.saveOptional(registries).toString()` 进行 NBT 序列化。在大网络（数万种物品）场景下，这会产生显著的 CPU 开销 |
| **建议** | 考虑使用 `AEItemKey` 的 `toTag()` 或 `hashCode() + equals()` 作为指纹，避免全量 NBT 序列化。仅在需要区分 NBT 差异时进行序列化 |
| **影响范围** | [`ae2/zone/ZoneMergePlanner.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/ZoneMergePlanner.java) |
| **优先级** | 🔴 高 |
| **实现状态** | ✅ 已实现（2026-05-28） |
| **实现摘要** | `ItemFingerprint` 从 `record(String itemId, String serializedStackNbt)` 重构为 `record(String itemId, int componentHash, int damageValue, long[] enchantData)`。`fingerprintOf()` 使用 `AEItemKey.hashCode()`（O(1) 已缓存）替代完整 NBT 序列化，配合耐久值 (`damageValue`) 和附魔 bitset (`enchantData`) 区分同一物品的不同状态。`indexAssignments()` 中的 NBT 反序列化改为一次性操作（仅在 `plan()` 调用时执行），不影响每次扫描的性能。 |

#### 3.2.4 [`RuntimeCell`](../类职责/ae2/zone/RuntimeCell.md) 的 `containsExactItem()` — 全量遍历性能问题

| 项目 | 内容 |
|------|------|
| **问题** | [`RuntimeCell.containsExactItem()`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/RuntimeCell.java) 每次调用都遍历 `getAvailableStacks()` 的所有条目。在 [`RuntimeZone.doPlanPlacement()`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/RuntimeZone.java) 中，每个候选 cell 都会调用此方法，形成 O(n*m) 的复杂度 |
| **建议** | 考虑在 `RuntimeCell` 中缓存一个 `Set<AEItemKey>` 或使用 storage 的 `getAvailableStacks()` 结果构建索引。注意缓存失效策略（cell 内容变化时） |
| **影响范围** | [`ae2/zone/RuntimeCell.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/RuntimeCell.java)、[`ae2/zone/RuntimeZone.java`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/zone/RuntimeZone.java) |
| **优先级** | 🟡 中 |

### 3.5 AE2 API 利用优化

#### 3.5.1 使用 `IStorageService` 替代 [`DriveMachineAccessor`](../类职责/ae2/scan/DriveMachineAccessor.md) 的反射扫描

| 项目 | 内容 |
|------|------|
| **问题** | 当前通过 [`DriveMachineAccessor.findSupportedDrives()`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/scan/DriveMachineAccessor.java) 遍历 `grid.getMachineClasses()` 来发现 drive。AE2 的 `IStorageService` 提供了更直接的存储挂载访问方式 |
| **建议** | 评估是否可以通过 `grid.getStorageService()` 获取已挂载的存储列表，减少对反射的依赖。注意：`IStorageService` 提供的是存储视图而非 drive 视图，可能需要权衡 |
| **影响范围** | [`ae2/scan/`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/scan/) 包 |
| **优先级** | 🟢 低 |

#### 3.5.2 [`CellCapacityInspector`](../类职责/ae2/CellCapacityInspector.md) 的反射 — 可考虑使用 `ICellHandler` 替代

| 项目 | 内容 |
|------|------|
| **问题** | [`CellCapacityInspector`](../../src/main/java/com/knightcode/appliedstoragesorter/ae2/CellCapacityInspector.java) 使用反射调用 `getTotalBytes`、`getUsedBytes` 等方法。AE2 的 `ICellHandler` 提供了标准化的 cell 访问接口 |
