# 整体逻辑

## 1. 当前主骨架

这个项目现在已经不是“做一个能动的方块”这么简单了，主骨架已经比较清楚：

> **玩家输入 -> 规则决策 -> zone 规划 -> zone 运行时 -> 搬运执行 -> 日志诊断**

同时，围绕 `/sorter me storageDump` 又形成了一条与执行主线并行、但同样重要的宏观观测主线：

> **live network -> storage analyzer -> dashboard snapshot -> 节点语义审核 -> world override -> 后续复用**

真正被搬运和整理的底层对象依然是：

> **Cell**

DAV、管理卡、profile、zone 都是在帮助系统决定：

- 某类 item 应该归到哪个 zone
- 某个 zone 在当前网络里应该落到哪个 cell

而 storage dashboard / 节点语义主线则是在帮助系统回答：

- 当前网络整体长什么样
- 哪些节点在主导存储
- 哪些节点带有特殊语义
- 哪些智能默认可以直接采用，哪些需要用户纠偏

---

## 2. 六层职责

### 2.1 玩家输入层
玩家直接接触的是：

- `DigitalAssetVaultBlock`
- `DigitalAssetVaultBlockEntity`
- `DigitalAssetManagementCardItem`
- `DigitalAssetVaultMenu`
- `DigitalAssetVaultScreen`
- `ZoneStampedManagementCardRecipe`

这一层负责：

- 让玩家声明 zone
- 让 DAV 成为 zone 容器
- 让输入具有可视化和可持久化形式

这一层**不负责**路由决策和搬运执行。

### 2.2 规则决策层
核心对象：

- `RoutingProfile`
- `ItemFilter`
- `RouteRule`
- `RoutingEngine`

这一层只回答：

> **item 应该去哪一个 zone**

它不知道 AE2 网络里有哪些 cell，也不知道最终会插入哪个 drive 槽位。

### 2.3 规划层
规划层当前有两条来源不同、目标一致的链路：

- 离线：`ZoneAllocationPlanner`
- 在线：`LiveZoneAllocationPlanner`

它们都会产出：

- `ZoneAllocationPlan`
- `ItemZoneAssignment`

也就是说，规划层负责把：

- dump 或 live grid 中的 item 事实
- 变成 item -> zone 的计划

但还**不会**直接决定具体 target cell。

### 2.4 Zone 运行时层
核心对象：

- `RuntimeZoneRegistryBuilder`
- `RuntimeTopology`
- `ZoneManager`
- `RuntimeZone`
- `RuntimeCell`
- `ZonePlacementDecision`

这一层的职责是：

1. 根据 DAV 等设备声明，建立 runtime zone
2. 维护 zone 下当前有哪些可操作 cell
3. 回答某个 item 进入 zone 时：
   - 能不能接
   - 应该落到哪个 cell
4. 维护 zone 内部的接纳策略与容量治理边界，例如：
   - placement / admission 规则
   - 黑名单 / 白名单等 zone-local 约束
   - zone 视角下的可用性判断

这一层是当前架构最关键的“桥”：

> **把逻辑 zone 接到真实 cell。**

同时需要明确一个执行边界：

- `RuntimeZone` / `ZoneManager` 负责 zone-local 的接纳、落点、治理策略
- 不负责真正的 `extract -> insert -> rollback` 执行事务
- 不负责技术日志、trace、metrics 收集
- 不负责 analyzer 风格的解释输出

### 2.5 分析 / dashboard 语义层
核心对象：

- `Ae2StorageAnalyzer`
- `StorageAnalyzerReport`
- `SorterStorageAnalysisService`
- `SorterStorageAnalysisDumpWriter`
- storage dashboard
- storage semantics override（后续）

这一层负责：

1. 从 live AE2 network 中提取宏观事实
2. 生成适合 dashboard 消费的 snapshot
3. 提出可解释的节点语义候选（例如疑似无限容器）
4. 为用户提供“智能默认 + 原地纠偏”的治理入口

这一层当前**不负责**：

- 直接执行搬运
- 替用户做不可撤销的最终语义判定
- 直接介入规则层 route 决策

它的定位更接近：

> **AE2 网络的观测、解释与语义审核层。**

### 2.6 执行与诊断层
核心对象：

- `Ae2ZoneMoveExecutor`
- `SorterPlanFileLogger`
- `SorterFileLogger`
- `SorterMergeReportFileLogger`

这一层负责：

- 真正执行 extract -> insert -> rollback
- 记录足够详细的日志，便于定位问题
- 为 `/sorter merge` 生成前后对比型复盘报告

执行层不重新做 route，不重新定义 zone 策略。

这里还需要补充两个约束：

- 更复杂的回滚一致性判断，属于执行层或其后续薄协作者，不属于 logger，也不属于 zone 管理侧
- metrics / trace / sample / debug 汇总，属于观察与诊断基础设施，不应继续塞进 `RuntimeCell` 这类运行时原语中

## 3. 当前存在的三条能力路径

### 3.1 主路径：plan / planAndMove
现在更推荐理解和继续扩展的是这条链：

1. `/sorter me bindProfile`
2. `/sorter me plan`
3. `/sorter me planAndMove`

内部大致是：

1. `Ae2ControllerTargetResolver` 找到 grid
2. `NetworkProfileBindingStore` / `RoutingProfileRepository` 找到 profile
3. `LiveZoneAllocationPlanner` 生成 live plan
4. `RuntimeZoneRegistryBuilder` 构建 `RuntimeTopology`
5. `Ae2ZoneMoveExecutor` 执行 zone move
6. `SorterPlanFileLogger` 输出详细日志

这条链路已经体现了当前项目真正的结构。

### 3.2 简化 merge 路径：/sorter merge
当前还保留一条面向低复杂度使用场景的命令路径：

- `SorterMergeService`
- `MergeMovePlanner`
- `SorterMoveOperation`
- `SorterMergeReportFileLogger`

这条链路专门负责：

- 把同类物品尽量合并到更少的 cell
- 为不想配置 profile / zone / DAV 的玩家提供快速入口
- 作为未来 GUI / 控制面板中的“快速 merge”按钮后端
- 输出可直接做价值展示的 merge report

当前 `/sorter merge` 已经不只是执行命令，还会同时产出两层日志：

1. `logs/appliedstoragesorter.log`
   - 记录 merge preview / execute 摘要
   - 记录 detailed merge report 路径
2. `logs/appliedstoragesorter/merge-*.log`
   - 记录 merge 前后分布位置、占用 cell、类型槽、已用字节、释放字节、释放可用组数
   - 记录收益最高的物品排行
   - 记录单物品 before / after、moved_out_from、merged_into 等明细

所以它不是规则化治理主线，但它是**刻意保留的简化 merge 模式**，并且现在已经具备更完整的复盘能力。

### 3.3 宏观观测 / dashboard 路径：/sorter me storageDump
当前已经形成一条新的长期主线：

- `SorterStorageAnalysisService`
- `SorterStorageAnalysisDumpWriter`
- `Ae2StorageAnalyzer`
- storage dashboard
- 存储节点语义层

这条链路专门负责：

- 导出 AE2 网络宏观快照
- 识别 dominant storage / fragmentation / health
- 发现疑似无限容器等语义节点
- 以 dashboard-first 方式向用户呈现结果
- 让用户对智能默认结果做低成本纠偏

这条路径当前不是执行链路，但它是：

> **后续宏观调控体验的主界面基础。**

## 4. 当前边界为什么是健康的

因为几个关键边界已经分开了：

### 4.1 规则层不碰运行时
- `RoutingEngine` 不依赖 Minecraft / AE2
- `RoutingProfile` / `ItemFilter` / `RouteRule` 是纯模型

### 4.2 运行时层不重做规则层
- `RuntimeZone` 只做 zone -> cell
- `Ae2ZoneMoveExecutor` 只消费 plan，不自行决定 route
- `ZoneManager` / `RuntimeZone` 可以承载 zone-local 的 admission / placement / policy 约束
- 但 blacklist / whitelist、容量治理等策略不应反向污染执行事务实现细节

### 4.3 玩家输入层不承担后端规划
- DAV 负责表达意图
- 管理卡负责携带 zone 数据
- 不直接承担规划和搬运职责

### 4.4 分析层独立于游戏主流程
- `analysis/**`
- `profilegen/**`

这些工具都可以离线运行，不会污染在线命令链。

### 4.5 dashboard 语义层不直接越权执行
- analyzer 可以提出候选项与智能默认
- dashboard 可以展示并允许用户纠偏
- 最终 world override 应作为事实层被后续流程消费
- 这条链路不应直接跳过用户，把推测硬写成不可撤销事实

## 5. 当前最需要记住的事实

### 5.1 zone 是语义，不是最终落点
- `StorageZone` 是逻辑定义
- `RuntimeZone` 是运行时实例
- `RuntimeCell` 才是实际操作单位

### 5.2 DAV 是管理入口，不是架构中心本身
DAV 很重要，但它的真正价值是：

- 让玩家声明 zone
- 让 runtime zone 能在网络里被构建出来

真正执行整理时，系统最后操作的仍然是 cell。

### 5.4 dashboard 主场的目标是“先给结果，再让用户纠偏”
对于 storage dashboard / 节点语义主线，当前已经明确一个产品原则：

- 高度可疑节点可以默认按 infinite-like 处理
- 这样用户打开 dashboard 时就能先看到尽量正确的宏观结果
- 若系统判断有误，用户再原地标记“不是无限容器”

也就是说：

> **开箱即用优先，但默认假定不等于最终事实。**

---

## 6. 一句话结论

当前项目的真实结构可以概括为：

> **玩家用 DAV / 管理卡声明治理意图，规则层决定 item -> zone，运行时层把 zone 落到 cell，执行层完成实际搬运；同时 analyzer 与 dashboard 主线负责输出网络宏观视图、提出节点语义假定，并让用户以最低摩擦完成纠偏。**
