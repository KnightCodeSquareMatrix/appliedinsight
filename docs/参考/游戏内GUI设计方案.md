## 1. 设计目标

游戏内 GUI 是玩家与 Applied Energistics: Insight 交互的主场景之一，另一主场景是外部 Web Dashboard。二者的分工遵循以下原则：

| 场景 | 定位 | 典型用户 |
|------|------|---------|
| **游戏内 GUI** | 日常操作、快速执行、状态检查 | 所有玩家（含生存模式） |
| **外部 Dashboard** | 宏观分析、深度洞察、语义纠偏 | 管理员、重度用户 |

游戏内 GUI 的设计哲学：

> **让玩家在游戏内完成日常治理操作，无需退出游戏或打开浏览器。**

## 4. 各 GUI 详细设计

### 4.1 A — SorterCommandBlock 增强（P0）

#### 4.1.1 设计目标

> 让玩家从命令方块 GUI 获得完整的操作体验，**无需依赖 chat 消息**获取反馈。

#### 4.1.2 布局设计

```
┌─────────────────────────────────┐
│  命令执行方块                     │  ← 标题行
│  ─────────────────────────────── │
│  ● ME 网络已连接  Zone: 主存储    │  ← 状态栏（网络状态、绑定信息）
│  ─────────────────────────────── │
│                                 │
│  操作命令区                       │
│  ┌─────────┐ ┌─────────┐       │
│  │ 🔍 扫描  │ │ 📊 分析  │       │  ← 左列：观测命令
│  │  网络    │ │  存储    │       │
│  └─────────┘ └─────────┘       │
│  ┌─────────┐ ┌─────────┐       │
│  │ 📋 生成  │ │ 🚀 规划  │       │  ← 右列：规划与执行
│  │  计划    │ │  并搬运  │       │
│  └─────────┘ └─────────┘       │
│  ┌─────────┐                    │
│  │ 🔗 整理  │                    │  ← 底部：Merge（独立路径）
│  │  合并    │                    │
│  └─────────┘                    │
│  ─────────────────────────────── │
│  📄 上次结果: 2026-05-28 14:32   │  ← 反馈栏（可点击展开）
│  扫描网络 完成 ✓  共 24 个节点    │
│  [查看详情 >]                    │
└─────────────────────────────────┘
```

#### 4.1.3 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 反馈方式 | **GUI 内嵌状态栏 + 可折叠详情** | 不依赖 chat，玩家直接在 GUI 看到结果摘要 |
| 纹理 | **自定义纹理**（替代 hopper） | 品牌识别，匹配 DAV 纹理风格 |
| 状态栏 | **顶部静态条** | 一眼看到网络状态、绑定 profile、zone 信息 |
| 操作按钮 | **带图标 + 颜色区分** | 蓝色=观测，红色=执行，绿色=Merge |
| 上次结果 | **底部栏 + 点击展开** | 不占用主区域，需要时才查看 |

#### 4.1.4 交互流程

```
玩家右键点击 SorterCommandBlock
  → 打开增强 GUI
  → 点击 [扫描网络]
    → 按钮变灰 "执行中..."
    → 后端执行 -> 结果通过 SorterCommandPayload 回传
    → GUI 底部反馈栏更新摘要
    → 按钮恢复可用
  → 玩家可点击 [查看详情 >] 打开结果查看器（C1/C2）
```

#### 4.1.5 需要的后端支持

| 需求 | 说明 |
|------|------|
| 结果回调 Payload | 当前 `SorterCommandPayload` 是单向（C→S），需要新增 `SorterCommandResultPayload` （S→C）携带结构化结果 |
| 网络状态查询 | 新增查询接口，让 GUI 初始化时获取网络状态、绑定 profile 等元信息 |
| 结果 URL/ID | 每条命令执行结果应有唯一 ID，方便 GUI 引用和详情查看 |

#### 4.2.3 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| Zone 信息面板 | **顶部可折叠面板** | 不占用 cell 操作区域，需要时展开 |
| Cell 槽颜色指示 | **边框着色（绿/黄/红）** | 直观反映 cell 健康状态，无需 hover |

| 物品种类/碎片 | 轻量查询 ME 网络 | 打开 GUI 时 |

### 4.3 C — 结果查看器 GUI（P1）

#### 4.3.1 为什么需要结果查看器

当前所有命令执行结果通过 **chat 消息** 返回：

```
[Sorter] 扫描完成: 发现 24 个存储节点
[Sorter] 分析完成: 碎片化程度 medium
[Sorter] 计划已生成: 将移动 42 个物品到 zone "主存储"
```

**问题**：
- Chat 消息是瞬时的，玩家容易错过
- 结构化数据无法在 chat 中良好展示
- 多次操作的结果无法对比
- 无法查看详情（如"哪些物品被移动"）

结果查看器将**缓存的后端数据可视化**，让玩家在游戏内也能查看分析/计划/Merge 的详细结果。

### 5.4 数据流

```
[玩家点击按钮]
  → SorterCommandPayload 发送到服务端
  → 服务端执行命令（SorterDumpService / SorterPlanService / ...）
  → 服务端发送 SorterCommandResultPayload 返回客户端
  → 客户端缓存数据（ClientStorageAnalysisCache / ClientPlanCache）
  → 更新 SorterCommandBlockScreen 底部反馈栏
  → 玩家点击 [查看详情 >] 打开结果查看器 Screen
  → 结果查看器从缓存读取数据渲染
```

## 7. 与外部 Dashboard 的关系

> 游戏内 GUI ≠ 外部 Dashboard

二者不重复，而是互补：

| 能力 | 游戏内 GUI | 外部 Dashboard |
|------|-----------|---------------|
| 日常操作 | ✅ 一键触发 | ❌ 不适合 |
| 快速状态 | ✅ 摘要展示 | ✅ 详细分析 |
| 宏观分析 | ❌ 屏幕空间有限 | ✅ 图表/treemap/Lorenz |
| 语义纠偏 | ⚠️ 最小化（标记无限） | ✅ 完整纠偏体验 |
| 配置编辑 | ⚠️ 基础编辑 | ✅ 完整编辑器 |
| 历史趋势 | ❌ 不适合 | ✅ 数据库支持 |

**核心原则**（来自 [`dashboard的设计哲学.md`](dashboard的设计哲学.md)）：
> 游戏内 GUI 负责 **"日常操作 + 快速状态"**，外部 Dashboard 负责 **"宏观分析 + 深度纠偏"**。
> 二者通过同一套后端服务共享数据，不重复实现业务逻辑。

## 8. 设计约束

### 8.1 架构约束

1. **Screen 不包含业务逻辑** — 只负责渲染和交互，不参与 routing/planning/execution（FACT-050）
2. **网络包只负责传输** — `XxxPayload` + `XxxPayloadHandler` 不包含业务逻辑（FACT-050）
3. **缓存层薄** — `ClientXxxCache` 只做数据和反序列化，不做业务聚合
4. **不绕过命令系统** — GUI 操作最终通过命令/网络包触发，不直接调用服务端 Service

### 8.2 UX 约束

1. **先给结果，再让用户修正** — 所有 GUI 打开时就有可用数据，不需要先配置
2. **不靠 chat 作为主要反馈通道** — GUI 内应自包含状态和反馈
3. **不要求复杂配置后才能使用** — 一键操作优先
4. **保持与 AE2 视觉风格一致** — DAV 纹理沿用 AE2 Drive 风格，SorterCommandBlock 匹配

### 8.3 性能约束

1. **结果查看器数据量控制** — 列表超过 50 条时分页，单页不超过 20 条
2. **不阻塞主线程** — 数据加载、分页在 Screen tick 中完成
3. **缓存优先** — 已获取的数据优先从缓存读取，避免重复网络请求
