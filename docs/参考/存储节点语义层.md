# 存储节点语义层 (Storage Node Semantics)

> 本文档定义存储分析中的"节点语义"概念：如何从原始存储数据中推断节点的角色和意图。
> 这是 dashboard 和 storageDump 功能的核心理论基础。

---

## 1. 什么是节点语义

在 AE2 网络中，每个存储位置（cell slot / storage bus）都有其物理属性（容量、类型、占用率），
但用户对它的**意图**是额外的语义层：

| 物理属性 | 语义推断 |
|---------|---------|
| 容量极大、类型数极少 | 可能是**批量存储节点**（bulk storage） |
| 容量极小、类型数极多 | 可能是**样本/展示节点** |
| 物品总量极大（>10亿） | 可能是**无限容器**（drawer、无限单元） |
| 外部存储且物品极多 | 可能是**外部批量存储** |
| 碎片化程度高 | 可能是**混合节点**，需要拆分 |

**核心原则**：后端分析器只产生**可解释的候选项**，不做最终语义判定。
最终语义由用户在 dashboard 中确认/纠偏。

## 2. 语义推断维度

### 2.1 容量维度

| 指标 | 来源 | 语义含义 |
|------|------|---------|
| `totalBytes` | `CellCapacityInspector` | 物理容量上限 |
| `usedBytes` | `CellCapacityInspector` | 已用容量 |
| `byteUsageRatio` | `usedBytes / totalBytes` | 容量使用率 |
| `totalItemTypes` | `CellCapacityInspector` | 最大可存种类数 |
| `remainingItemTypes` | `CellCapacityInspector` | 剩余可存种类数 |
| `cellKind` | 由 `totalBytes` 推导 | 如 `64k_cell`、`256k_cell` |

### 2.2 分布维度

| 指标 | 来源 | 语义含义 |
|------|------|---------|
| `occurrenceCount` | 物品在 cell 间的分布数 | 碎片化程度 |
| `internalTotalAmount` | 内部 cell 总量 | 可控存储 |
| `externalTotalAmount` | 外部 storage bus 总量 | 外部存储依赖 |
| `externalAmountDominant` | `externalTotalAmount > 80%` | 外部存储主导 |

### 2.3 健康维度

| 指标 | 阈值 | 语义含义 |
|------|------|---------|
| `fragmentationScore` | > 2.5 = high, > 1.25 = medium | 碎片化程度 |
| `isNearlyFull` | `byteUsageRatio > 0.8` | 容量告警 |
| `isTypeExhausted` | `remainingItemTypes < 5` | 类型耗尽告警 |
| `healthLevel` | good / warning / critical | 综合健康等级 |

### 2.4 无限容器检测

通过启发式关键词匹配识别疑似无限容器：

```java
Set<String> INFINITE_STORAGE_KEYWORDS = Set.of(
    "creative", "unlimited", "infinite", "无限", "创造"
);
```

检测逻辑（[`CellCapacityInspector.java`](../src/main/java/com/knightcode/appliedstoragesorter/ae2/CellCapacityInspector.java)）：
1. Mod ID 白名单匹配（如 `storagedrawers`、`laserio` 等已知无限 mod）
2. Cell 物品 ID 关键词匹配
3. 容量异常大（`totalBytes == 0` 或 `totalBytes` 极大）的 cell

## 3. 语义候选类型

分析器（[`Ae2StorageAnalyzer.java`](../src/main/java/com/knightcode/appliedstoragesorter/ae2/analysis/Ae2StorageAnalyzer.java)）产生以下语义候选：

| 候选类型 | 触发条件 | 建议动作 |
|---------|---------|---------|
| `suspected_infinite_storage` | 关键词匹配或 mod 白名单 | 在 dashboard 中标记为无限容器 |
| `high_fragmentation` | `fragmentationScore > 2.5` | 建议 merge 或重新规划 zone |
| `external_amount_dominant` | 外部存储占比 > 80% | 建议将外部存储纳入 zone 管理 |
| `nearly_full` | `byteUsageRatio > 0.8` | 建议扩容或迁移 |
| `type_exhausted` | `remainingItemTypes < 5` | 建议清理或换用更大 cell |
| `unassigned_cell` | `zoneId == null` | 建议分配到 zone |

## 4. 语义层与 dashboard 的关系

```
后端分析器 (Ae2StorageAnalyzer)
  │
  ├── 产生 StorageAnalyzerReport
  │     ├── summary (宏观统计)
  │     ├── storageLocations (每个存储位置的详情)
  │     ├── itemDistributions (物品分布)
  │     ├── healthFlags (健康信号列表)
  │     └── suspectedSemanticCandidates (语义候选)
  │
  ├── 序列化为 storage-analysis-*.json
  │
  └── dashboard 消费
        ├── 展示健康信号和语义候选
        ├── 用户确认/纠偏语义判定
        └── 用户 override 持久化到游戏端
```

**关键原则**（详见 [`docs/dashboard的设计哲学.md`](dashboard的设计哲学.md)）：
1. **先给结果，再让用户修正** — dashboard 打开就有可用数据
2. **高度可疑节点默认按无限容器假定处理** — 避免统计污染
3. **默认假定不等于最终事实** — 用户可以在 dashboard 中纠偏
4. **用户的主要操作应是"纠偏"，而不是"先配置后可用"**
