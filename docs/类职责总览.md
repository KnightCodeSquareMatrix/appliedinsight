## 2. 本次审查结论

已逐个查看 `src/main/java` 下的 **98 个 Java 类型**，结论如下：

### 2.1 整体边界是健康的
当前项目已经基本形成以下边界：

- **入口/装配层**：`AppliedStorageSorter`、各类 `registry`
- **命令/应用服务层**：`SorterCommands`、`SorterPlanService` 等
- **AE2 集成层**：`ae2/**`
- **纯规则层**：`rule/**`
- **离线分析层**：`analysis/**`
- **规划模型层**：`plan/**`
- **玩家输入与界面层**：`block`、`blockentity`、`item`、`menu`、`client`
- **日志基础设施层**：`logging/**`

最重要的一点是：

> **规则层没有被 Minecraft / AE2 运行时依赖污染。**

这说明核心边界是守住了的。

### 2.2 当前已经形成第三条长期主线
除了：

- profile / zone / plan / move 主线
- `/sorter merge` 简化路径

现在还应明确一条新的长期主线：

- `/sorter me storageDump`
- storage analyzer snapshot
- storage dashboard
- 节点语义层
- world save override（后续）

这条链路的定位不是执行搬运，而是：

> **提供 AE2 网络的宏观观测、解释、智能默认与用户纠偏能力。**

### 2.3 没有发现明显的“大而空抽象”
当前代码没有出现这些常见问题：

- 为未来想象提前做一整套框架
- 把简单 DTO 硬拆成 service / manager / provider 三层
- 让 route、zone、cell、execute 混成一个抽象体系

相反，当前抽象大多是“被真实需求逼出来的”：

- `ZoneManager` / `RuntimeZone`
- `RuntimeCell`
- `RuntimeTopology`
- `RoutingEngine`
- `ZoneAllocationPlan`

这些抽象都是有实际调用链支撑的，不属于过度设计。

### 2.3 当前主要技术债只有少数几处
目前最值得长期盯住的，不是大面积架构问题，而是少量明确技术债：

1. `DriveMachineAccessor`
   - 使用反射和 block id 白名单适配 drive-like 机器
   - 当前很实用，但升级上游实现时要重点回归
2. `MergeMovePlanner`
   - `/sorter merge` 的合并路径仍在使用
   - 它和新的 zone 规划/执行链路并存，但定位已经明确为“快速 merge 模式”
3. `SorterMergeService`
   - 负责 `/sorter merge`
   - 它不是 legacy 残留，而是面向低复杂度使用场景的保留入口

## 3. 当前推荐的理解方式

### 3.1 主线运行链路
当前真正的执行主线可以概括为：

> **玩家输入 -> profile -> route -> zone plan -> runtime zone -> execute -> log**

对应对象：

- 玩家输入：`DigitalAssetManagementCardItem`、`DigitalAssetVaultBlockEntity`
- 路由规则：`RoutingProfile`、`RoutingEngine`
- 规划：`LiveZoneAllocationPlanner`、`ZoneAllocationPlan`
- 运行时 zone：`RuntimeTopology`、`RuntimeZone`、`RuntimeCell`
- 执行：`Ae2ZoneMoveExecutor`
- 诊断：`SorterPlanFileLogger`

### 3.2 merge 路径仍存在，但不是规则治理主线
当前仍然保留一条快速 merge 路径：

- `SorterMergeService`
- `MergeMovePlanner`
- `SorterMoveOperation`

这条链路能工作，而且有明确产品价值：

- 快速合并杂物
- 降低使用门槛
- 未来适合作为 GUI / 控制面板中的简化入口

所以它不是 profile/zone 主线，但它也不是应当被忽视的历史残留。

### 3.3 宏观观测 / dashboard 主线也应单独理解
当前 storage analyzer 路线应理解为：

> **live network -> storage analyzer -> dashboard snapshot -> 节点语义审核 -> world override -> 后续复用**

对应对象：

- `SorterStorageAnalysisService`
- `SorterStorageAnalysisDumpWriter`
- `Ae2StorageAnalyzer`
- `StorageAnalyzerReport`
- storage dashboard

这条路径的价值在于：

- 给用户一个开箱即用的宏观网络视图
- 识别 dominant storage / fragmentation / health
- 对高度可疑节点采用智能默认
- 允许用户在 dashboard 原地纠偏，而不是先进入笨重配置流程

当前项目最可贵的地方不是“类很多”，而是：

> **这些类大多已经待在正确的层里，并且抽象基本服务于当前真实需求；同时项目已经开始从“会搬运”扩展到“会观测、会解释、会给出智能默认并允许用户纠偏”的宏观调控方向。**
