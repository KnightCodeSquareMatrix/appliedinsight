> **拓扑已经干净，接下来先把 logger 做强。**

---

## 2. 本阶段主目标

本阶段的核心目标不是“到处加日志”，而是：

1. 明确 logger 的分层与边界
2. 建立统一的运行时技术日志方案
3. 保留并强化 plan / merge / dump 这类报告型输出能力
4. 避免日志需求反向污染 runtime / application / analyzer 的职责

本阶段重点是：

> **把 logger 明确收敛为基础设施。**

---

## 3. 当前正式原则

### 3.1 logger 一律视为基础设施

无论什么情况，logger 都属于基础设施。

这条原则现在正式成立，并作为后续重构的硬边界使用。

它的含义是：

- `RuntimeTopology`、`RuntimeZone`、`Ae2MoveAnalyzer`、`Ae2ZoneMoveExecutor` 等核心类
  不应为了 logger 需求而扭曲自身职责
- 核心层负责产生：
  - 运行时事实
  - 决策结果
  - 结构化 report / result / debug report 对象
- logger 负责：
  - 文本渲染
  - 文件写入
  - 技术运行日志输出
  - 导出格式组织

### 3.2 区分两类日志能力

#### A. 技术运行日志
统一采用：

- `SLF4J`
- Lombok `@Slf4j`
- 占位符风格日志输出

适用场景：

- 生命周期信息
- 调试信息
- warn / error
- 异常上下文
- 关键运行时分支观测
- 非用户导出型日志

判断标准：

> 面向开发者、运行时、排错过程的日志，走 `SLF4J + @Slf4j`。

#### B. 报告型输出
继续保留专门基础设施类自行拼装内容并落盘，例如：

- plan 输出
- merge 报告
- dump 输出
- analysis 导出
- debug report 文件

判断标准：

> 面向文件产物、稳定文本结构、审计/归档/导出用途的内容，不走普通技术日志，而由专门的输出器自己拼装。

也就是说：

- `dump` 自己拼
- `merge` 自己拼
- `plan` 自己拼
- 但它们本质上仍然属于基础设施

## 4. 本阶段的重点工作

### 4.1 统一技术日志方案

目标：

- 在项目内建立一致的技术日志风格
- 不再混用零散的日志写法
- 后续类引入运行日志时有统一落点

预期动作：

1. 引入并确认 `SLF4J` 使用方式
2. 使用 Lombok 自动生成 logger 实例（如 `@Slf4j`）
3. 统一占位符风格，避免字符串拼接式技术日志
4. 统一 info / debug / warn / error 的使用语义

完成标准：

- 技术运行日志有清晰统一写法
- 新旧代码在引入运行日志时有明确规范可依

### 4.2 强化报告型 logger

目标：

- 让 plan / merge / dump / analysis 这类输出器成为真正可依赖的基础设施能力
- 允许它们继续自己拼内容，但边界更清楚、结构更稳定

预期动作：

1. 盘点现有 logger / writer：
   - `SorterPlanFileLogger`
   - `SorterFileLogger`
   - `SorterMergeReportFileLogger`
   - dump / analysis writer
2. 区分“运行日志”和“报告输出”两种职责
3. 提取必要的共享文件写入/头部/时间戳/路径组织逻辑
4. 保持现有文件格式可读性，不急于引入复杂 logging framework

完成标准：

- 报告型输出器边界清晰
- 共享基础能力得到收敛
- 不再把它们误认为普通程序日志

### 4.3 明确 logger 不反向定义核心模型

目标：

- 防止后续为了“好打日志”而污染 runtime / analyzer / application 设计

硬规则：

1. 不允许因为 logger 需求，让 `RuntimeZone` 直接生成大段文本
2. 不允许因为 logger 需求，让 `RuntimeTopology` 暴露多余格式化接口
3. 不允许把 report 对象和 logger 本身混为一谈
4. 核心层先产结构，logger 再做表达

## 5. 本阶段建议顺序

### 阶段 A：先更新文档与原则

先把以下认知冻结下来：

1. logger 一律属于基础设施
2. 技术运行日志使用 `SLF4J + Lombok @Slf4j`
3. dump / merge / plan / analysis 保持专门输出器自行拼装
4. logger 不反向塑造核心模型

### 阶段 B：建立技术日志规范

先不大面积改代码，而是优先确定：

- 哪些类需要技术运行日志
- 哪些类只需要报告型输出
- 哪些地方当前日志职责混杂

### 阶段 C：开始收 logger 基础设施

优先检查并整理：

- `logging/**`
- `ae2/dump/**`
- 可能存在的 report writer / file writer

重点不是做大框架，而是：

- 统一风格
- 提取共享能力
- 降低重复
- 明确边界

---

## 6. 本阶段明确不做的事

近期先不做：

1. 不继续扩展 `RuntimeTopology` 的语义范围
2. 不在这一步正式扩展 analyzer 为大系统
3. 不把 logger 改造成复杂 observability 平台
4. 不引入沉重 logging framework 替代现有报告输出器
5. 不为了“日志统一”而重写 plan / merge / dump 的核心业务逻辑
6. 不让 logger 需求反向决定 zone runtime responsibility

一句话：

> **这一步做的是 logger 基础设施收敛，不是借 logger 名义再做一轮大重构。**

---

## 7. 当前的判断标准

新增或修改 logger 相关结构前，先问：

1. 它是不是明确属于基础设施？
2. 它是在强化运行日志能力，还是在污染核心模型？
3. 它是在提升导出/排错/可维护性，还是只是在形式上“更像框架”？
4. 它有没有把技术运行日志与报告型输出混在一起？

只有这些问题都说得清，才值得继续做。

---

## 8. 下一步最可能的执行任务

如果继续推进代码改造，最合适的方向是：

1. 先建立 `SLF4J + @Slf4j` 的统一使用基线
2. 再审计 `logging/**` 与 dump writer 的职责分布
3. 然后做一轮“小而硬”的 logger 基础设施收敛：
   - 共享写文件能力
   - 共享 header / metadata 输出
   - 保持各类报告各自独立拼装正文

下一步最值钱的工作不是继续折腾 topology，而是：
