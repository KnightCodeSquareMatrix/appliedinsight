# 前端对接说明

## 1. 前端边界

前端当前不再只需要稳定对接 routing profile，还要逐步承接：

- **storage dashboard**
- **节点语义确认**
- **智能默认结果的纠偏**

当前前端需要重点对接四类内容：

1. **routing profile JSON**
2. **React Query Builder metadata**
3. **storage analyzer snapshot / semantic review payload**
4. **me-dump JSON（新增容量字段）** — 每个 cell 现在携带 `totalBytes` / `usedBytes` / `totalItemTypes` / `remainingItemTypes` / `cellKind` / `zoneId`，前端可直接用于存储健康诊断，无需后端预分析

此外，若后续接入“快速 merge”结果展示，前端还可以把 `/sorter merge` 的详细 report 作为**结果展示型日志输入**，但它不是 profile 契约，也不是运行时执行接口。

前端当前仍然**不需要**理解这些运行时实现细节：

- AE2 grid
- DAV capability
- runtime zone registry
- 搬运执行过程

前端不负责运行时执行，它负责的是：

- 表达玩家规则意图
- 展示网络宏观事实
- 呈现系统建议
- 让用户对智能默认结果做低成本纠偏

---

## 2. 当前最核心的边界结论

本次按类审查和 storage analyzer 讨论后，可以明确两件事：

> **前端契约层和运行时执行层是分开的。**

> **dashboard 是宏观调控主界面之一，但不是运行时执行器。**

对应关系是：

- 前端生成：`RoutingProfile`
- 后端规则层消费：`RoutingProfileJsonCodec` + `RoutingEngine`
- 运行时层消费规则结果：`LiveZoneAllocationPlanner` / `ZoneAllocationPlan`
- AE2 执行层真正搬运：`Ae2ZoneMoveExecutor`

也就是说，前端的终点仍然是：

> **定义 item 应该去哪个 zone；展示网络实际状态；承接用户对节点语义的确认或纠偏。**

而不是参与决定 target cell 或直接执行搬运。

补充一点：

- `/sorter merge` 详细报告更适合作为“价值展示 / before-after 复盘”输入
- 它可以被前端读取后渲染成对比卡、delta 行、top benefit items 等视图
- 但当前它仍属于日志产物，不应被误当作稳定写回契约

## 4. Query Builder 对应关系

### `FilterGroup`
- `combinator` -> Query Builder `combinator`
- `rules` -> Query Builder `rules`

### `FilterCondition`
- `field` -> Query Builder `field`
- `operator` -> Query Builder `operator`
- `value` -> Query Builder `value`

当前 filter 已经是树结构：

- `root`
- `FilterGroup`
- `FilterCondition`

前端不应该再假设“只有一层 conditions + matchMode”。

## 5. 前端必须遵守的规则

### 5.1 不要自定义枚举常量
前端应直接使用后端导出的值，不要手写：

- field
- operator
- combinator
- zone kind
- route action

### 5.2 保存前必须做 schema 校验
至少拦截：

- `zones[].kind` 缺失
- `routeRules[].action` 非法
- `defaultZoneId` 未指向已有 zone
- `filterId` / `targetZoneId` 为空字符串

### 5.3 profile 只负责规则层
前端生成的是：

- zone
- filter
- route rule
- default zone

前端**不负责**：

- 决定具体 cell
- 决定运行时搬运顺序
- 决定 zone 内部整理逻辑
- 决定 DAV 在网络中的实时映射

### 5.4 dashboard 先给结果，再让用户纠偏
对于 storage dashboard，前端应遵守一个额外原则：

> **先展示智能默认结果，再允许用户原地纠偏。**

这意味着：

- 不要要求用户先完成一整套语义配置，才能看到可用 dashboard
- 对高置信度疑似无限节点，前端应优先展示“当前已默认按 infinite-like 处理”的结果
- 如果该判断不对，用户应能直接在 dashboard 中标记“不是无限容器”
- 专门语义配置页未来可以存在，但它应是补充入口，不应成为主入口

## 6. 后端如何消费前端结果

当前消费路径有两条：

### 6.1 Profile 主线

1. 前端生成 profile JSON
2. `RoutingProfileJsonCodec` 读取 profile
3. `RoutingEngine` 决定 `item -> zone`
4. `LiveZoneAllocationPlanner` 或 `ZoneAllocationPlanner` 生成 plan
5. 运行时再结合 `RuntimeTopology` / `RuntimeZone` / `RuntimeCell` 完成实际搬运

所以边界非常清楚：

- 前端负责**表达规则**
- 后端负责**落地执行**

### 6.2 Storage dashboard / 节点语义主线

1. 后端通过 `/sorter me storageDump` 导出 storage analyzer snapshot
2. 前端读取 snapshot，展示 overview / storage list / item distribution / health
3. analyzer 若输出疑似语义节点（例如疑似无限容器），前端应直接在 dashboard 中展示其理由与当前默认处理状态
4. 对高置信度节点，前端应允许用户原地执行最小操作：
   - 确认它确实是无限容器
   - 标记它不是无限容器
   - 暂不处理
5. 前端把审核后的最小 JSON 结果写回游戏端
6. 游戏端把 override 持久化到 world save，并在后续 analyze / plan 中应用

这条链路的关键点是：

- analyze 负责**提出候选项与理由**
- dashboard 负责**默认展示智能结果，并允许低成本纠偏**
- 游戏端负责**保存事实并复用**

特别注意：

- 高度可疑节点可以默认按 infinite-like 处理，以保证 dashboard 开箱即用
- 但这种默认处理不是最终事实，用户必须能够轻松改成“非无限”

## 8. 一句话结论

前端后续不只是 profile 编辑器，还会是：

> **AE2 网络 storage dashboard、节点语义审核与智能默认纠偏界面。**

当前仍需保持边界清晰：

- profile 路线负责**表达规则**
- storage dashboard 路线负责**展示网络事实、采用智能默认、允许用户原地纠偏**
- 运行时执行仍由游戏端后端完成

如需理解 dashboard 产品取向，优先阅读：

- `docs/dashboard的设计哲学.md`
- `docs/存储节点语义层.md`
